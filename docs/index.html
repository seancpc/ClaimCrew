醫療保險理賠多代理審核系統（ClaimCrew）

Multi-Agent Medical Insurance Claims Review on Azure Managed Services

全 Azure 託管、零自建基礎設施 · LLM 判事實、程式管放行 · 73 案全量回歸放行錯 0 · 開發期雲端總花費 NT$2,189、拆除後每日 $0 · 全合成資料零 PHI
▶ Demo 影片 原始碼(GitHub) 架構決策紀錄(ADR)

保險公司收到理賠申請(診斷證明書 + 醫療收據 + 申請書)後,系統完成文件抽取、保單條款比對(帶原文引用)、 初審判定與人工覆核路由。核心設計是模型只負責判讀事實,放行由程式決定:核付金額由程式從明細加總並反查條款, 47 種確定性檢核任一未過即轉人工。成本也是一級工程目標 —— 不需雲的工作先以 $0 完成,完成後以 Bicep 全拆。

設計概念

  • 壓縮計費窗口:合成資料、schema、Gate、eval、prompt、Bicep 在建立任何 Azure 資源之前全部完成 —— 計費時鐘最後才啟動,付費期只做「只有雲上能做的事」。
  • LLM 判事實、程式管放行:模型填判定與算式材料、指出條款段落;程式加總金額、填入引文原文,再由 Gate 反查條款、限額、日數、等待期與信心門檻 —— 任一未過即轉人工。
  • 拆建即成本控制:完成後全拆(常駐費 $0),repo 保存「可重生一切的原料與腳本」而非產物;需要 demo 時以 Bicep + 重建 Runbook 重建。

專案簡介

  • 任務:理賠案三分類(核付 / 拒付 / 需人工)+ 核付金額計算,每筆判定逐條綁定條款引用。
  • 驗證規模:3 份虛構保單(住院定額 / 手術定額 / 實支實付,共 100 條)、73 件合成理賠案(核付 41 / 拒付 23 / 人工 9;含等待期、既往症、除外責任、限額截斷、文件矛盾等陷阱案型),真值人工逐案檢核後凍結為 eval set。
  • 開發投入:約 100 小時 AI 協作開發(依 commit 時戳估算,為下限)、543 commits、37 份 SPEC、10 份英文 ADR。

成效亮點

  • LLM 判事實、程式管放行:每一個「讓 LLM 自己修正後放行」的實驗都留下對應的 Gate 漏洞,所以模型沒有放行權;Azure 的 groundedness 與 Prompt Shields 也實測後才否決接入,結論和證據寫成 10 份 ADR。
  • 成本是一級工程目標:不需上雲的工作(資料、schema、Gate、eval、Bicep)全部先以 $0 完成,Azure 最後才開;抽取改用 gpt-4.1-mini 後每案成本降 33.8%,eval 不退步;完成後用 Bicep 全拆,拆除後每日 NT$0。
  • 證據先於宣稱:每次改動前先寫好判準,以至少 3 輪歷史區間判斷是否退步,不符就撤回(SPEC-ab、SPEC-x 都因此撤回);把「放行錯」改成雙向計數後,挖出舊口徑漏掉的 6 件錯誤自動拒付;1,362 個測試加上 225 個手寫變異全數殺死。
  • 事件驅動、無金鑰:上傳請求檔 → Event Grid → Storage Queue → Container Apps Job 自動執行,全程使用 Entra 受控身分與 RBAC,沒有任何 API key;Job 只在執行時計費,閒置時 Container Apps 費用為 0。
  • 程式填引文:模型只指出條款段落,引文原文由程式從條款庫填入,「模型抄錯引文」這類假旗標從大宗降到 v17 的 0 件。

開發歷程

開發過程不是「一路成功」,而是一連串「遇到問題 → 驗證 → 誠實修正」。以下是幾個關鍵節點:

① coverage 100%、測試全綠,為什麼還是有洞?

解決方式:對 schema 轉換層跑手動變異測試,mutant M3(拿掉陣列巢狀物件的強制邏輯)在 13 個測試全綠、行覆蓋 100% 下存活 —— 既有測試只驗了「現有模型的輸出」,從未直接驗函式核心語意。補上手構 inline 巢狀結構的直接單元測試後復殺,最終 6/6。這是「覆蓋率是偵測器不是目標」的具體實證。

② PDF 顯示正常,抽取回讀卻全是亂碼?

解決方式:合成文件 PDF 首版用 CID 字型(MSung-Light),檢視器顯示完全正常,但 pdfplumber 抽文字回讀成錯亂漢字 —— 根因是 CID 字型不寫入 ToUnicode 對照表,顯示正確不代表文字層正確。改嵌入 TTF(wqy-zenhei)後回讀正確;「生成檔案必做抽取回讀驗證」自此成為固定紀律。

③ demo 不用時的閒置月費,怎麼歸零?

解決方式:採「拆建即成本控制」—— 全拆後常駐費 $0,需要時以 Bicep 重建。關鍵想通的一點:repo 該保存的是可重生一切的原料與腳本(DI 訓練樣本 + 標註、條款 PDF + 建索引腳本),而非產物本身(custom 模型不可匯出)。實測兩次全拆:27 分 → 15 分,拆除後隔日帳單歸零。

④ 40 件理賠案的真值金額,怎麼避免手算轉錄錯誤?

解決方式:首批 10 案手寫並人工核算;擴量 30 案改為模板 × 參數的程式化生成,真值金額由與條款參數同一份定義的確定性計算器產出,推導式自動組出、逐案附於真值檔。日數慣例(含入出院日)寫死在單一函式,消滅「同一慣例散落多處」的漂移空間。

⑤ 40 案真值我自己驗全綠,人工檢核卻抓出 7 個錯

解決方式:案件、條款、真值三者都由同一套產生器產出,自我一致不等於正確——若對條款的理解有偏差,三者會一起錯且錯得完全一致,任何自動檢查都抓不到。於是出一份逐案檢核表交人工判定,核出 6 個錯,最嚴重的是把「文件不全補正」掛到「詐欺與不實告知」條;修正時又連帶發現第 7 個(術式不在附錄表)。共通點是跨檔案的語意一致性(條號 ↔ 條文內容、案型標籤 ↔ 欄位數值),程式只能驗結構與算術。教訓一句話:AI 出的題不能由 AI 自己閱卷。

⑥ 讓 LLM 修補被攔下的案件再放行,準確率明明上升,為什麼否決?

解決方式:Repair agent 以 Gate 為工具重判被攔下的案件,外加六道確定性防護。兩輪全量重放,Gate 後正確率確實上升(0.694 → 0.792),但每輪都放行一件金額錯:一次模型縮小收據金額來湊限額檢核(C003 −2,000),一次修對了類別卻撞上 Gate 沒有的分段限額檢核(C055 +5,000)。每一件放行錯都對應一個 Gate 漏洞,修補層等於把「幸運轉人工」變成損失。結論:Repair 改為顧問模式、無放行權,漏洞改用確定性檢核補上(ADR-008)。

⑦ Azure 的 groundedness 偵測能抓模型捏造嗎?

解決方式:先證明 API 本身是決定性的(10 案 × 3 次,極差 0),再用已知答案的對照對測鑑別力:捏造的既往症主張 0/3 被抓到,有源頭的合法拒付卻 3/3 被判捏造,乾淨案的日數主張 12/12 誤報。API 把「推論句」當捏造、把「條款詞彙出現」當有據,與理賠裁決的任務型態不合 —— 不接主管線。Prompt Shields 對中文注入 0/2 命中,而既有的「抽取 → schema → Gate」邊界在 9 個注入變體下放行 0、判定翻轉 0(ADR-009)。
